# Заявки сайта и подписки Telegram / MAX

`worker.mjs` — серверная часть отдельного сервиса Sites. GitHub Pages отдаёт только сайт. Закрытая D1 хранит заявки, подписки, состояние ввода пароля и очередь отправки. Публичный API: https://prioritet-leads-20261105.eggetsevich.chatgpt.site.

## Подписка

Открыть https://t.me/prioritetzaiavkibot или https://max.ru/id482108371165_1_bot, отправить `/start`, затем указанный владельцем пароль. Каждый прошедший проверку получатель подписывается независимо; ручные username/chat_id не нужны. `/status` показывает подписку, `/stop` отключает её. После пяти попыток ввода пароля действует пауза 15 минут. Пароль не сохраняется в базе или исходниках.

Telegram в шапке ведёт в существующий клиентский аккаунт ателье. Клиентская ссылка MAX с `start=client` предлагает опрос сайта и телефон; она не подключает посетителя к служебной рассылке.

## Хранение и доставка

- `POST /api/leads` атомарно сохраняет заявку и уведомления всем активным подписчикам. `requestId` предотвращает повторное создание заявки; изменённые данные с тем же ключом отклоняются.
- `accepted: true` означает сохранение. `delivered: true` появляется только после успешного ответа API хотя бы одного получателя. Без подписчиков заявка сохраняется в закрытой базе; последующие новые заявки направляются подключённым получателям.
- Webhook-события защищены отдельными секретами и обрабатываются без повторного изменения состояния. MAX использует отправителя, а не идентификатор бота из recipient.
- Очередь хранится в D1. Неудачные отправки остаются с увеличивающейся задержкой; очередь повторно обрабатывается при следующих обращениях к API или событиях ботов. Безусловная exactly-once доставка внешними платформами не гарантируется.
- Публичного чтения заявок нет. `/health` выдаёт только состояние подключения. `/internal/verify`, `/internal/configure`, `/internal/self-test` требуют серверный `ADMIN_TOKEN`. Самопроверка не отправляет уведомлений и удаляет только собственную синтетическую запись.
- Секреты задаются native Sites environment variables. Frontend знает лишь публичный `PUBLIC_LEAD_API_URL`.

## Развёртывание

Рабочий checkout сервиса: `../prioritet-leads-api`. Его `.openai/hosting.json` содержит отдельный Sites ID и D1 binding `DB`; не переносить ID в GitHub Pages проект. Worker копируется отсюда в `worker/index.js` сервиса. Схема создаётся миграцией Drizzle до запуска; `worker-schema.sql` — её копия для локальных проверок. Обновления публикуются через Sites source workflow, saved version и deploy. Секреты в исходники не переносятся.

Для MAX настроен проверенный официальный `https://platform-api.max.ru` с проверкой TLS. Также разрешён актуальный `https://platform-api2.max.ru`; перед переключением проверить доверие сертификату на хостинге. Перенаправления API не выполняются, чтобы токен не передавался другому адресу.

MAX получает события через Cloudflare Pages Function `functions/webhooks/max.js` на домене сайта: `https://mebel-6c2.pages.dev/webhooks/max`. Она передаёт исходный JSON и подпись в сервис, который проверяет секрет и обрабатывает событие. Токены в Pages Function не хранятся. `MAX_WEBHOOK_URL` в серверных настройках сохраняет этот адрес при повторной настройке; без переменной остаётся совместимость с прямым webhook сервиса. На GitHub Pages серверные Functions не выполняются. После смены домена нужно обновить адрес и регистрацию MAX. `npm run test:webhooks` проверяет подпись, предел размера, передачу ошибок и запрет ложного подтверждения.

## Проверка

`npm run test:leads` использует локальную SQLite и подставные API. Проверяет обе платформы, несколько подписчиков, пароль, блокировку попыток, status/stop, повторные события/заявки, защиту webhook, CORS, согласие, ошибки доставки и пять шагов опроса. Реальных сообщений не отправляет.
